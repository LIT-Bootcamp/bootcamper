# TICKET-002: Enforce confirmation-proof lifecycle

## Business outcome
Learners can confirm email ownership only with the current valid proof, while failed proof attempts leave account state private and unchanged.

## Scenario traceability
IDEA-009/v003; EPIC-001/v002; SCENARIO-004, SCENARIO-005, SCENARIO-006, SCENARIO-007, SCENARIO-008, SCENARIO-012.

## User/system flow
1. SCENARIO-004 normal path: an inactive learner follows valid current confirmation proof; the system marks email ownership confirmed and tells the learner ordinary sign-in is available.
2. SCENARIO-005 invalid proof: a learner presents malformed or unknown proof; the system changes no account state and returns the same generic invalid-link guidance used for any failed confirmation.
3. SCENARIO-006 expired proof: a learner presents expired proof; the system changes no account state and returns the same generic invalid-link guidance used for any failed confirmation.
4. SCENARIO-007 used proof: a learner presents already-used proof; the system changes no account state and returns the same generic invalid-link guidance used for any failed confirmation.
5. SCENARIO-008 superseded proof: a learner presents proof issued before the newest proof; the system changes no account state and returns the same generic invalid-link guidance used for any failed confirmation.
6. SCENARIO-012 blocked account path: a blocked learner confirms with valid current proof; the system records email ownership, tells the learner the account remains unavailable for ordinary sign-in, and keeps the blocked state unchanged.

## Technical implementation
Use Devise Confirmable at the confirmation controller boundary. Validate token authenticity, freshness, used state, and newest-proof status before applying the confirmed transition; on blocked accounts, persist confirmation without changing the external blocked state or session eligibility.

## Change surface
Likely paths: `app/models/user.rb`, Devise confirmation controller/customization, confirmation result views, locale copy, `spec/models/user_spec.rb`, and `spec/requests/confirmations_spec.rb`.

## Data and security notes
Store confirmation proof so old and used tokens cannot confirm the account. Failed confirmation attempts must not reveal whether an email exists, whether an account is blocked, or which private account state caused the failure.

## Acceptance evidence
`spec/requests/confirmations_spec.rb` covers SCENARIO-004 valid current proof confirming ownership and proving the sign-in-ready success guidance. The same request spec covers SCENARIO-005 invalid proof, SCENARIO-006 expired proof, SCENARIO-007 used proof, and SCENARIO-008 superseded proof with no account mutation and one generic invalid response. `spec/requests/confirmations_spec.rb` covers SCENARIO-012 confirming ownership while preserving blocked state, rendering the still-blocked success guidance, and denying ordinary sign-in.

## Out of scope
No confirmation resend form, registration form changes, sign-in flow changes, block/unblock administration, recovery proof lifecycle, or production mail-provider setup.

## Dependencies and external actions
Dependencies: none. External actions: configure production confirmation URL host and email delivery.

## Estimate
6-8 hours.

## Definition of Done
Each mapped proof state has request coverage, invalid proof attempts preserve account state behind one generic failure response, valid confirmation uses only the current proof, blocked accounts remain blocked, and focused specs pass.

# TICKET-002: Enforce confirmation-proof lifecycle

## Observable goal

Learners can confirm email ownership only with the current valid proof, while failed proof attempts leave account state private and unchanged. A valid proof confirms a blocked learner without restoring ordinary sign-in eligibility.

## Source IDEA, EPIC, version, and scenario IDs

IDEA-009/v003; EPIC-001/v002; SCENARIO-004, SCENARIO-005, SCENARIO-006, SCENARIO-007, SCENARIO-008, SCENARIO-012.

## Acceptance evidence

`spec/requests/confirmations_spec.rb` proves valid-current confirmation (SCENARIO-004); invalid, expired, used, and superseded proofs leave account state unchanged (SCENARIO-005 through SCENARIO-008); and a blocked learner is confirmed without mutation of the blocked state (SCENARIO-012). TICKET-011 supplies the persisted block state and the request proof that correct blocked credentials cannot start a session.

## Dependencies

TICKET-011

## Difficulty (1-5)

3

## Estimate (ideal days, at most 2)

1.5

## Risks

Token handling can disclose private account state or accept an old, expired, or used proof. Confirmation must not clear or otherwise alter the blocked state supplied by TICKET-011.

## External actions

Configure the production confirmation URL host and email delivery.

## Allowed scope

Devise Confirmable token lifecycle, confirmation-controller outcome, confirmation result copy, mailer URL configuration, and focused confirmation specs. No blocked-state persistence or authentication-policy implementation, resend form, registration flow, block/unblock administration, recovery proof lifecycle, or production mail-provider setup.

# EPIC-001 technical analysis

## Feasibility evidence

`User` currently uses Devise Confirmable but has no persisted blocked state or authentication-eligibility override. `ConfirmationsController#show` calls `User.confirm_by_token`, while `SessionsController` uses Devise's default session behavior. Therefore the current Rails code cannot prove SCENARIO-012's requirement that confirmation preserves a blocked account and ordinary sign-in remains unavailable. TICKET-011 establishes that prerequisite before TICKET-002 owns confirmation behavior.

## Coverage

TICKET-001 covers SCENARIO-001, SCENARIO-002, and SCENARIO-003. TICKET-002 covers SCENARIO-004, SCENARIO-005, SCENARIO-006, SCENARIO-007, SCENARIO-008, and SCENARIO-012's confirmation transition. TICKET-011 covers SCENARIO-012's persisted blocked state and sign-in denial. TICKET-003 covers SCENARIO-009, SCENARIO-010, and SCENARIO-011.

## Risks

Privacy response differences, resend races, delivery failures, a confirmation path that mutates the blocked state, and a sign-in hook that bypasses existing Devise confirmation checks. Existing-session invalidation is deliberately not duplicated here; it remains TICKET-004.

## External actions

Configure the production confirmation host, sender, and email delivery. The external administrator-owned system must use the agreed persisted blocked-state transition.

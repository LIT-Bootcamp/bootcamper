## Ticket contract

### Problem

Provide the identity record needed by later registration and admin-workspace tickets, with role and email invariants enforced by both Rails and PostgreSQL.

### Acceptance criteria

- [ ] Users support exactly `student` and `admin` roles.
- [ ] New users default to `student`.
- [ ] Email is required and unique case-insensitively at the database level.
- [ ] PostgreSQL rejects unsupported roles even when Rails validations are bypassed.
- [ ] RSpec coverage proves roles cannot be combined.

## Approved plan and Q&A

### Plan

1. Add a `users` table with normalized email, scalar string role, default student role, and timestamps.
2. Add a PostgreSQL check constraint for the two supported roles and a unique functional index on `LOWER(email)`.
3. Add the `User` model with Rails enum, role validation, email normalization, presence, and case-insensitive uniqueness validation.
4. Add focused model specs using direct records; the E1-05 test-stack dependency is explicitly waived for this ticket.
5. Run focused and static checks, preserve unrelated E1-02/E1-03 work, and prepare a sanitized immutable review packet.

### Scope decisions

- Password/authentication fields remain deferred to E3-02.
- Admin seeding remains deferred to E1-04/E3-01 follow-up account setup work; this ticket creates the role capability only.
- A role is one scalar value, not a set, so a user cannot hold both roles.
- Email normalization strips surrounding whitespace and downcases before validation.

## Technical decisions

### TD-1 — String-backed scalar role

Use a PostgreSQL-compatible string enum rather than bit flags or multiple role tables. This keeps the two-role MVP explicit, prevents accidental role combinations, and leaves a future authorization redesign possible if requirements expand.

### TD-2 — Database uniqueness is case-insensitive

Use a unique functional index on `LOWER(email)` in addition to the model validation. Application validation gives useful errors; the index is the concurrency-safe invariant.

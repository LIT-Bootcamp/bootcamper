## Ticket contract

### Problem

Verify that a registered student controls the supplied email address before future application access.

### Acceptance criteria

- [x] Registration sends an expiring confirmation link.
- [x] A confirmation link is single-use.
- [x] Unverified users cannot apply to courses when that application boundary exists.

### Approved requirement clarifications

- Confirmation links expire after three days.
- No resend-confirmation endpoint is included.
- No placeholder course-application boundary is added; provide a verified-user predicate seam only.
- Account creation persists if delivery infrastructure is unavailable.
- Confirmation success uses a separate localized page.
- Full sign-in/reset/admin authentication remains out of scope.

## Approved plan and Q&A

### Plan

1. Add Devise Confirmable fields and integrate the module with the existing User model.
2. Configure a three-day confirmation window and safe test/development mailer URL defaults.
3. Send confirmation instructions after registration without automatic sign-in, preserving the account if delivery fails.
4. Add confirmation token handling, separate localized success/error responses, and a verified-user predicate seam.
5. Add model/request/mailer coverage, run checks, self-review, and produce an immutable handoff.

## Technical decisions

### TD-1 — Use Devise Confirmable with a custom confirmation boundary

- Context: Registration is custom and later sign-in/application tickets are not implemented.
- Decision: Use Devise’s token generation/confirmation machinery, send instructions from the registration boundary, and expose only explicit confirmation routes with a separate success page.
- Alternatives: Hand-rolled tokens or generated full Devise routes; rejected because they duplicate security-sensitive token behavior or expand authentication scope.
- Consequences: User gains confirmation fields and `email_verified?`; later application authorization can depend on that predicate.

## Challenges

- No course-application endpoint exists, so the acceptance guard can only be represented by the tested predicate seam in this ticket.
- Devise’s mapping and custom mailer URL adapter are required because the application intentionally exposes custom confirmation routes rather than generated Devise routes.

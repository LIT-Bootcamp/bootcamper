## Ticket contract

### Problem

Local and deployed configuration needs a documented, secret-safe source with clear failure when required values are absent.

### Acceptance criteria

- [x] Environment-specific Rails encrypted credentials are configured and documented.
- [x] Required database values are read from credentials without silent defaults.
- [x] Missing keys fail clearly without exposing secret values.
- [x] Key files and plaintext credentials are ignored; no secrets are committed.
- [x] Compose/CI use credential-backed configuration without direct database secrets.

### Approved requirement clarifications

- Do not add `dotenv-rails` or use `.env` for Rails configuration.
- Use `development`, `test`, and `production` encrypted credentials with ignored keys.
- Production supplies encrypted credentials and `RAILS_MASTER_KEY` externally.
- Compose requires credential-backed configuration; no direct-variable fallback.
- Required keys are `database.host`, `database.username`, `database.password`, and `database.name`.
- `.env.example` may document approved key names only; it contains no database values.

## Technical decisions

### TD-1 — Rails encrypted credentials

- Context: Database configuration currently uses environment variables and defaults.
- Decision: Use per-environment encrypted credentials and fail closed when keys are absent.
- Alternatives: dotenv or direct Compose/CI variables.
- Consequences: Developers must create local credential files/keys before boot; production secrets stay outside Git.

## Challenges

- Development/test encrypted payloads intentionally contain only non-secret `CHANGE_ME` placeholders and must be replaced locally. Production credentials remain external. PostgreSQL was unavailable for live verification.

## Ticket contract

### Problem

Users who forget their password need a secure, expiring recovery flow without revealing whether an email exists.

### Acceptance criteria

- [ ] A reset request returns the same localized response whether or not the email exists.
- [ ] A known email receives an expiring, single-use reset link.
- [ ] A valid link accepts a new password and rejects the old password.
- [ ] Resetting a password invalidates existing sessions.
- [ ] Reset completion does not automatically sign the user in.

## Approved requirement clarifications

- Retain Devise’s six-hour reset-token expiry.
- Use explicit custom password routes while keeping `devise_for :users, skip: :all`.
- Enable Devise paranoid reset-request behavior.
- Do not automatically sign in after reset; require a normal E3-04 login.
- Preserve accounts and generic responses if mail delivery is unavailable.
- Do not add rate limiting, resend, MFA, social login, or other recovery features.

## Approved plan and Q&A

### Plan

## Technical decisions

### TD-1 — Devise Recoverable with explicit custom boundary

- Context: The application already owns registration, confirmation, and session routes while retaining Devise internals.
- Decision: Enable only `recoverable`, expose explicit reset routes, and reuse the custom `UserMailer` URL boundary.
- Alternatives: Hand-rolled reset tokens or all generated Devise routes; rejected because they duplicate security-sensitive behavior or expand scope.
- Consequences: Devise manages token expiry/consumption and password-salt session invalidation while the UI remains localized and project-owned.

- Local PostgreSQL and browser server binding may be unavailable; CI/Compose is the fallback.
- Existing E3-03/E3-04/.codex worktree changes are unrelated and must remain untouched.
